# Blender 5.2 LTS intervention map — 2026-08-25

## Research question

Across the Blender 5.2 film-production stack, where can Blender Film Studio intervene beyond UI automation and build deterministic, testable production infrastructure?

## Scope and evidence rule

This audit covers film-production control surfaces, not every UI command in the Blender manual. Claims about Blender 5.2 come from Blender Foundation, Blender Developer Documentation, and versioned API/manual pages. Intervention depth, determinism and priority are engineering judgments made by this project and are explicitly separated from official feature claims.

## Core finding

Deep intervention is technically viable. The highest-value target is not an unconstrained agent that writes arbitrary `bpy` code. It is a closed production system:

`Intent → validated SceneSpec → deterministic Blender compiler → shot scene → EEVEE/Cycles → EXR/AOV → validator → localized rebuild`

Blender 5.2 makes this route more practical through:

- official RNA properties for Geometry Nodes modifier inputs and outputs;
- `gpu.init()` for GPU-backed background execution;
- remote HTTP asset libraries with versioned listings, hashes, license metadata and preferred import methods;
- Geometry Bundles, Lists and broader data types for cross-object declarative node systems;
- USD color-space tagging, Alembic animated camera/visibility import and expanded glTF export;
- broader input color spaces, Cycles texture caching, interactive compositor improvements and faster FP16 OpenEXR writing.

The major warning is equally explicit: the new Geometry Nodes hair/cloth physics system is experimental in 5.2, and the official Blender MCP executes model-generated Blender code without built-in safety guards.

## Intervention scale

| Level | Meaning | Acceptance test |
|---|---|---|
| L0 | Observe | State and dependencies can be inventoried without mutation |
| L1 | Parameterize | Existing controls can be changed and restored predictably |
| L2 | Proceduralize | Reusable templates and node assets construct bounded content |
| L3 | Compile | Validated SceneSpec deterministically creates a shot package |
| L4 | Close the loop | Render, validation and dependency-aware partial rebuild are automated |

The project should target L3 and L4. Script generation alone is L1–L2.

## Six first-stage engineering packages

1. **SceneSpec + Blender Compiler** — schema, permissions, idempotent builders, scene diff and operation log.
2. **Asset Registry** — stable IDs, remote listing, licenses, versions, dependencies and import policy.
3. **Procedural Factory** — typed node groups, versioned inputs, fixture scenes and bake registry.
4. **Cinematography System** — camera grammar, lens profiles, lighting/look templates and EEVEE review mode.
5. **Render Delivery** — Cycles profiles, render telemetry, AOV/Compositor contract, EXR and manifest.
6. **Validator + Regression Lab** — structural, pixel, performance, cache and API compatibility tests.

## Explicit exclusions for phase one

- No arbitrary model-generated code executing directly against production `.blend` files.
- No claim that an LTS release is bug-free or cross-device identical without regression tests.
- No dependency on experimental Geometry Nodes physics as the only hero-cloth or hero-hair path.
- No assumption that USD, Alembic or glTF round-trips all Blender semantics.
- No attempt to automate cinematic taste, actor-level performance or arbitrary hero topology as if they were deterministic subsystems.

## First milestone

Use the baseline six-second interior shot. From the same SceneSpec, change lens, performance timing or one light rig parameter; rebuild only affected dependencies; produce EEVEE review, Cycles EXR/AOV output and a machine-readable difference report. The milestone passes only if two clean builds are structurally reproducible and failures point to a specific upstream input or build step.
