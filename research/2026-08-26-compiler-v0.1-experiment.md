# Blender Compiler v0.1 — B01/B02 structural experiment

Snapshot: 2026-08-26

Status: executed on native Blender 5.2.0 LTS (`fbe6228777e7`), macOS arm64

## Question

Can one restricted SceneSpec be converted into an immutable BuildPlan and compiled twice from a factory-empty Blender state with the same normalized scene structure?

The acceptance unit is a canonical manifest of assets, object types, transforms, camera and light parameters, Action Slot/Channelbag F-Curves, evaluated camera samples, frame settings, render settings, and pinned asset hashes. Raw `.blend` bytes are measured but are not the acceptance unit.

## Implemented chain

`SceneSpec → schema/semantic/security validation → verified canonical BuildPlan → Blender-side plan verification → asset re-hash → data API scene build → scene manifest → structural SHA-256`

The runtime compiler never executes Python from a SceneSpec or asset. It has no network path. All input assets must remain under allowed repository roots and match their declared SHA-256 before BuildPlan generation and again inside Blender.

## Benchmarks

### B01 — material still life

- Project-owned `.blend` collection with leather, brushed metal, glass, a skin-tone card, and a neutral stage.
- 58 mm camera, two area lights, one-frame scene.
- SceneSpec: `specs/benchmarks/B01.scene.json`.

### B02 — interior dolly

- Project-owned room and chair libraries.
- 144 frames at 24 fps.
- Restricted camera transform keys at frames 1 and 144 with linear interpolation.
- SceneSpec: `specs/benchmarks/B02.scene.json`.

## Results

| Check | B01 | B02 |
|---|---:|---:|
| BuildPlan deterministic | pass | pass |
| clean-build structure A = B | pass | pass |
| tampered BuildPlan rejected | pass | pass |
| `.blend` byte identity | fail | fail |
| calibrated ACES/OCIO | not tested | not tested |
| final pixel identity | not tested | not tested |

Structural hashes from the final recorded run:

- B01: `18d807d4467e5d647883ed58aa6989affa06a87e974f66ba402b28e1777ad6fe`
- B02: `d0bc5ffe1fcef749a0e27d9b2c9049f33664ce93f9509e8c3fc0dff7ae452a1f`

The two saved `.blend` files for each benchmark had different SHA-256 values. This is a useful negative result: scene reproducibility cannot be defined as raw container byte identity without first explaining and normalizing Blender's internal binary state. The canonical manifest remains inspectable and stable.

## Blender 5.2 runtime corrections

1. The actual EEVEE engine identifier in Blender 5.2.0 is `BLENDER_EEVEE`, not `BLENDER_EEVEE_NEXT`.
2. Multi-layer EXR requires `ImageFormatSettings.media_type = MULTI_LAYER_IMAGE` before assigning `OPEN_EXR_MULTILAYER`.
3. The legacy `Action.fcurves` API is removed. The compiler must access F-Curves through the assigned Action Slot and its Channelbag.
4. Camera interpolation is now included in the normalized manifest; B02 records nine transform F-Curves and evaluates start, midpoint, and end frames.
5. Saving the current scene still uses the documented `bpy.ops.wm.save_as_mainfile` boundary. Scene construction and asset append use `bpy.data` and `bpy.data.libraries.load`.

## Preview evidence

Four 960×540 EEVEE previews were rendered from the compiled scenes: B01 frame 1 and B02 frames 1, 72, and 144. They confirm that the compiler produced visible assets, lights, a camera, and a moving camera evaluation. They are not 4K EXR research masters and are not evidence of cinematic quality.

## Explicit non-claims

- No production-grade asset was tested.
- No actor, rig, facial animation, contact, simulation, or editorial conform was tested.
- No final Cycles frame was rendered.
- No OpenEXR channels or metadata were inspected.
- No OCIO configuration was pinned; therefore no calibrated ACEScg claim is made.
- No same-GPU or cross-GPU pixel tolerance was established.

## Next experiment

Define PixelSpec v0.1 and execute the first pixel reproducibility test:

1. Select and hash an ACES 2-compatible OCIO configuration.
2. Render B01 frame 1 and B02 frames 1, 72, and 144 at the research-master raster.
3. Validate OpenEXR channels, channel types, finite values, frame metadata, and per-file hashes.
4. Render each sample twice on the same device and compute exact and perceptual differences.
5. Preserve the negative result if denoising or device state prevents exact equality.
